# Reviewer Capability Resolution

Use this protocol to resolve stack reviewers without hardcoding framework names in shared workflows.

1. Resolve enabled plugins and transitive dependencies from each active project config, including core. When configuration is absent, infer the touched stack from manifests and state the inferred scope.
2. Classify the changed responsibilities from files, contracts, and actual call paths; read the matching enabled plugin indexes and ownership rules. A transitive shared UI/data plugin supplies conduct but does not automatically require a duplicate reviewer for the same responsibility.
3. For the requested role (`reviewer-deep`, `reviewer-business-logic`, or `reviewer-fast`), inspect each relevant **non-core** plugin's declared `paths.skills` directory and the matching role's `SKILL.md` frontmatter. Select leaf reviewers by their stated scope and responsibility, using actual names/paths rather than constructing names from technology strings. Exclude the invoking workflow and all shared orchestrators from leaf candidates; core remains eligible conduct and core-toolkit changes use the generic fallback.
4. Give every selected reviewer the same requested change set plus its responsibility slice and original requirement sources/decisions from `inputs-grounding-gate.md`. Include both sides of a real transport, renderer/host, UI/API, or persistence boundary; avoid reviewing the same layer twice solely because a shared dependency is enabled. Business-logic variants and the generic implementation fallback apply `behavioral-completeness.md`, including its risk-driven case generation; preserve independent inspection rather than handing over only the implementer's conclusions.
5. Add the generic quality or implementation fallback from [review-specialist-fanout.md](./review-specialist-fanout.md) for changed scope not owned by a selected reviewer, including conduct-only plugins. Load that scope's eligible indexes/risk rules; use a regression focus for fast review.
6. Resolve specialist gates once at the top level: deep review evaluates testing, documentation, and visual-reference gates; standalone business or fast review evaluates the visual-reference gate. A supplied design reference opens that fidelity gate when the changed UI is in scope, even when the user did not name the specialist. Full review takes the combined set once. Deduplicate by role plus responsibility; a child reviewer does not launch another copy of the review.
7. Report unavailable capability separately from unresolved findings. Keep each stack/responsibility, fallback, and specialist report under its own heading named from the resolved scope; do not require a fixed list of framework headings.
